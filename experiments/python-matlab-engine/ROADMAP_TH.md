# Roadmap: เรียนรู้วงจรกำลังและทดลอง Python → MATLAB/Simulink

จัดทำวันที่ 4 พฤศจิกายน 2026 จากบริบทแชท “ทดสอบ Python กับ MATLAB Engine” และการตรวจไฟล์แบบอ่านอย่างเดียว

## แผนปัจจุบัน — 7 พฤศจิกายน 2026

ผู้ใช้เลือก **DC Fast Charger for Electric Vehicle (R2026b)** สำหรับทดสอบเปลี่ยนค่าผ่าน Python แทนวงจร Bridge เดิม:
https://www.mathworks.com/help/releases/R2026b/simscape-electrical/ug/dc-fast-charger.html

- ลบชุดทดลอง `rectifier/` ในโปรเจกต์ตามคำขอแล้ว รวมโมเดล สคริปต์ประกอบ และไฟล์ autosave รวม 5 ไฟล์ ไม่ได้ลบต้นฉบับใน Documents/MATLAB/Examples
- เก็บ `smoke_test.py` ไว้ สถานะเดิมยังเป็น import Engine ผ่าน แต่ startup ไม่ผ่าน (`Transport stopped`); ยังไม่ทดสอบซ้ำ
- ผู้ใช้เก็บสำเนาโมเดลไว้ใน `dc-fast-charger/` และยืนยันชื่อไฟล์ที่โหลดจากโฟลเดอร์โปรเจกต์แล้ว ตัวอย่างประกอบด้วย Grid สามเฟส ภาค AC/DC ภาค isolated DC/DC และแบตเตอรี่
- ผ่านการทดลอง manual → Python → เว็บ local แล้ว: เป้าหมาย 40 A ได้กระแสตัวอย่างสุดท้าย 39.46074956936718 A ตรงกันระหว่าง Python กับหน้าเว็บ ตามผลและภาพที่ผู้ใช้ส่งวันที่ 7 พฤศจิกายน 2026
- ใช้ Python 3.13.18 ใน `.venv`, MATLAB Engine 26.2 และ Flask 3.1.3 เชื่อมกับ MATLAB ที่ผู้ใช้เปิดและแชร์ชื่อ `EVChargingLab` ผ่าน `connect_matlab` วิธีนี้ต่างจากการเปิด session ใหม่ใน `smoke_test.py` เดิม
- ขอบเขตเว็บ: HTML กรอกจำนวนเต็ม 20–100 A → Python ส่ง `target_current_A` เข้า Workspace → `manual_current_test.m` รันวงจร → อ่าน `last_current_A` → แสดงบนหน้าเดิม บันทึกใน Workspace สำหรับรอบนั้น ไม่มีฐานข้อมูล
- `web_app.py` ให้บริการเฉพาะ `127.0.0.1:5050` โดยรับงานทีละรายการ ดูการติดตั้ง บทบาทไฟล์ และวิธีรันใน [README.md](README.md)
- ตรวจต่อไป: เปลี่ยนค่าบนเว็บจาก 40 เป็น 50 A แล้วเทียบผล manual เดิมประมาณ 51.1445 A ยังไม่มีหลักฐานผลเว็บกรณี 50 A ในจังหวะที่บันทึกเอกสารนี้
- เริ่มจากตั้งค่าก่อนรันและอ่านผลหลังจบ เปลี่ยนทีละค่า พร้อม input/expected/check โดยคำนึงถึงตัวควบคุมของโมเดล
- การทดลองจริงข้างต้นเป็นการที่ผู้ใช้ลงมือรันและส่งผลให้ตรวจ การสอนยังทำทีละขั้น ไม่ขยายไปยังเว็บหลัก ฐานข้อมูล หรือฮาร์ดแวร์โดยอัตโนมัติ

> เนื้อหาตั้งแต่หัวข้อ 1 ด้านล่างเป็น **แผนเดิมและหลักฐานย้อนหลัง ณ 4 พฤศจิกายน 2026** ลำดับ Buck/rectifier และรายการขอบเขตเดิมถูกแทนที่ด้วยแผนปัจจุบันด้านบนแล้ว ส่วนวิธีเรียนทีละขั้นและการตรวจหลักฐานยังคงใช้

## 1. เป้าหมายของ phase นี้

ศึกษาว่าไฟจากระบบถูกแปลงและควบคุมจนเหมาะกับการชาร์จได้อย่างไร อุปกรณ์อิเล็กทรอนิกส์กำลังแต่ละส่วนทำหน้าที่อะไร โดยใช้วงจรตัวอย่างง่าย ๆ แล้วพิสูจน์ว่า Python สามารถส่งพารามิเตอร์ สั่งจำลอง และรับผลกลับมาตรวจได้

คำถามที่ต้องตอบเมื่อจบ:

1. วงจรเรียงกระแสแปลง AC เป็น DC อย่างไร และ capacitor ช่วยอะไร?
2. Buck converter ปรับแรงดัน DC ลงได้อย่างไร สวิตช์ ทางไหลกระแส ตัวเหนี่ยวนำ ตัวเก็บประจุ PWM และ feedback ทำหน้าที่อะไร?
3. Python ส่งอะไรเข้าไป MATLAB/Simulink คืนอะไร และเราตรวจความถูกต้องอย่างไร?

**ปรับแรงดันกับลดกำลังชาร์จต้องแยกกันเรียน** กำลัง DC เกี่ยวข้องกับทั้งแรงดันและกระแส (`P = V × I`) ผลจากโหลดตัวต้านทานยังไม่ใช่พฤติกรรมแบตเตอรี่จริง และค่า PWM 0–255 ในเว็บเดิมยังไม่ใช่ gate PWM ของ converter

## 3. พื้นที่และขอบเขตที่เสนอ

```text
ev-charging-simulation/
├── src/                         ระบบเว็บ EV เดิม
├── supabase/                    โครงสร้างฐานข้อมูลเดิม
└── experiments/
    └── python-matlab-engine/    พื้นที่เรียนรู้และทดลองแยก
        ├── ROADMAP_TH.md        เอกสารนี้
        └── smoke_test.py        สคริปต์เดิม ยังไม่ผ่านการรันครบ
```

ข้อเสนอคือเรียนวงจรเล็กสองส่วนแบบแยกรัน:

```text
ส่วน A: AC → bridge rectifier → capacitor → โหลดตัวต้านทาน
ส่วน B: แหล่งจ่าย DC → Buck converter → โหลดตัวต้านทาน
                              ↑
                       ค่าแรงดันอ้างอิง

Python → ตั้งค่าก่อนรัน → Simulink จำลอง → รับผลเมื่อจบ → ตรวจผล
```

เสนอเรียนส่วน B ก่อนเพื่อเจาะคำถาม “ปรับแรงดันลงได้อย่างไร” แล้วเรียนส่วน A เพื่อเติมความเข้าใจ AC → DC จากนั้นใช้ Python สั่งโมเดลที่พิสูจน์แล้ว การต่อสองส่วนเป็นระบบเดียวไม่ใช่เงื่อนไขจบ phase นี้ และต้องตกลงเพิ่มแยกต่างหาก

ใช้ตัวอย่าง DC Fast Charger ดูภาพรวมเท่านั้นในช่วงแรก ยังไม่จำลองตู้เต็มระบบ

## 4. สิ่งที่ต้องใช้และต้องเตรียม

| สิ่งที่ใช้ | สิ่งที่ต้องตรวจหรือเตรียมก่อนถึงขั้นนั้น |
|---|---|
| VS Code และ Terminal | ใช้โปรเจกต์เดิมที่เปิดแล้ว เรียนคำสั่งครั้งละหนึ่งคำสั่ง |
| MATLAB/Simulink และ Simscape | ตรวจการเปิดโมเดลและ dependency ของตัวอย่างที่เลือกเมื่อผู้ใช้ตกลง ยังไม่ถือว่าทุกโมเดลรันได้จากรายชื่อผลิตภัณฑ์ |
| ตัวอย่าง Buck และ rectifier | เลือกโมเดลให้ชัด เก็บสำเนาสำหรับทดลองในโฟลเดอร์นี้เมื่อได้รับข้อตกลง หากต้องดาวน์โหลดให้แจ้งก่อน |
| ชุดค่าตั้งต้น | บันทึกหน่วย ค่าโหลด จุดวัด solver, stop time, initial conditions และช่วงเวลาที่นำมาวัด |
| Python ที่เข้ากันได้ | ระบุ path/version/architecture ไม่ใช้คำว่า `python3` โดยสมมติว่าจะเป็น 3.12; path ใน cache ของ Codex อาจเปลี่ยนได้ |
| MATLAB Engine | แยกการตรวจ import ออกจากการเปิด session และการรับผลคำนวณ ต้องตกลงวิธีรันใหม่ก่อนลอง startup อีกครั้ง |
| กราฟและผลลัพธ์ | ตรวจแพ็กเกจที่มีอยู่ก่อน หากขาดให้รายงานก่อนติดตั้ง เก็บข้อมูลตัวเลขพร้อมหน่วยและค่าตั้งต้น ไม่เก็บแค่ภาพกราฟ |
| เกณฑ์ผ่าน | กำหนด expected result, ช่วง steady-state และ tolerance ก่อน Run ไม่เปลี่ยนเกณฑ์ย้อนหลังเพื่อให้ผลผ่าน |

ไม่ต้องมี Node server, Supabase หรือ ESP32 ทำงานเพื่อทดลอง phase นี้

## 5. ขั้นตอนและหลักฐานผ่าน

ทุกขั้นด้านล่างเป็นแผน ยังไม่ใช่คำสั่งให้ลงมือทั้งหมดรวดเดียว

| ขั้น | เรียนและทำอะไร | Input | Expected result | วิธีตรวจ / เงื่อนไขผ่าน |
|---|---|---|---|---|
| **0. ยืนยันแผน** | ตกลงวงจรแรก ลำดับ และสิ่งที่จะวัด | เป้าหมายและข้อเสนอในเอกสาร | เข้าใจว่า Buck ทำ DC/DC และ rectifier ทำ AC/DC | ผู้ใช้ยืนยันลำดับหรือปรับแผนก่อนลงมือ |
| **1. รู้จักพื้นที่** | ต่อจาก `pwd` ที่ผ่านแล้ว: ดู `ls` และ Git | โปรเจกต์ปัจจุบัน | แยกเว็บ ฐานข้อมูล และพื้นที่ทดลองได้ | รู้ตำแหน่งไฟล์ใหม่และรายการงานแก้ค้าง โดยไม่ reset หรือเปลี่ยน branch |
| **2. อ่านวงจร Buck** | เปิดตัวอย่าง ดูอุปกรณ์และ feedback ก่อน Run | โมเดลและค่าตั้งต้นที่เลือก | อธิบายทางเดินพลังงานและหน้าที่ของแต่ละส่วนได้ | ระบุ input/output พร้อมหน่วย และจุดวัดได้ |
| **3. รันค่าตั้งต้น** | ใช้สำเนาโมเดลและค่าดั้งเดิมใน Simulink | โมเดล ค่า solver และเวลาเดิม | จบ simulation ได้และได้กราฟแรงดัน/กระแสตามเวลา | ตรวจ error, สัญญาณ, หน่วย และพฤติกรรมตามตัวอย่าง เก็บเป็นผลอ้างอิง |
| **4. เปลี่ยนหนึ่งค่า** | เปลี่ยนแรงดันอ้างอิง โดยคงโหลดและค่าอื่น | `Vref` เดิมและค่าทดลองที่โมเดลรองรับ | แรงดันหลัง transient ติดตามค่าเป้าหมาย | วัดค่าเฉลี่ย ความคลาดเคลื่อน และ ripple ในช่วงที่ตกลง เทียบกับเกณฑ์ก่อน Run |
| **5. เรียน AC → DC** | รัน rectifier ค่าตั้งต้น แล้วเปลี่ยน C หนึ่งค่า | แหล่ง AC/โหลดเดิม และค่า C ที่ระบุ | เห็นความต่างของ AC, DC และ ripple ระหว่างกรณี | ตรวจแรงดัน/กระแสในช่วงเดียวกัน อธิบาย rectification กับ filtering แยกกัน |
| **6. Python ↔ MATLAB** | หลังตกลงวิธีรันใหม่ เปิด Engine ส่ง scalar/array และปิด session ของตน | `81` และเมทริกซ์ `[[1,4,9],[16,25,36]]` | รากที่สองเป็น `9` และ `[[1,2,3],[4,5,6]]` | ตรวจค่ากับขนาด array, MATLAB release และการปิด session; ถ้า startup ไม่ผ่านให้หยุดที่ขั้นนี้ |
| **7. Python สั่งโมเดล** | เริ่ม Buck หนึ่งกรณี แล้วกรณีเปลี่ยนค่า จากนั้นใช้แนวทางเดียวกันกับ rectifier | ชุด parameter และโมเดลที่ผ่านแล้ว | ได้เวลา แรงดัน กระแส และผลสรุปกลับมา | เทียบกับการรันโดยตรงด้วย settings/ช่วงวัดเดียวกัน ภายใน tolerance ที่ตกลง |
| **8. สรุปและจบ phase** | ทำชุดกรณีเล็ก ๆ ซ้ำและอธิบายผล | กรณีทดลองที่ตกลงไว้ | มี input/expected/actual/pass–fail, กราฟ และวิธีทำซ้ำ | ผู้ใช้อธิบายผลและข้อจำกัดได้ ก่อนเสนอ phase เชื่อมเว็บ |

หากโมเดล Buck ใช้ feedback ให้เริ่มจากเปลี่ยนค่าอ้างอิงแรงดัน ไม่สั่ง duty cycle ทับ controller พร้อมกัน ถ้าต้องการศึกษา duty โดยตรงให้ตกลงการทดลองอีกกรณีและเงื่อนไขของโมเดลก่อน

ตัวอย่าง Buck Converter ที่อ้างอิงในแชทใช้ DC 30 V และเป้าหมาย 15 V ตัวเลขนี้เป็นของตัวอย่างนั้น ไม่ใช่ค่าของ Buck ทุกตัวหรือของตู้ชาร์จจริง ต้องยืนยันชื่อโมเดลก่อนใช้เป็น expected result

## 6. ตรวจผลแบบ Software Engineer

ให้แยกปัญหาเป็นส่วนที่ตรวจได้:

1. โมเดลรันโดยตรงและมีผลอ้างอิงแล้วหรือยัง?
2. Python เปิด Engine และคำนวณตัวเลขไปกลับได้แล้วหรือยัง?
3. ใช้ input เดียวกันแล้ว Python สั่งโมเดลได้ผลตรงกับผลอ้างอิงหรือไม่?
4. เปลี่ยน parameter หนึ่งตัวแล้วผลเปลี่ยนตามเหตุผลหรือไม่?

โครงบันทึกต่อหนึ่งกรณี:

```text
Case ID / คำถามที่ต้องการพิสูจน์:
โมเดลและเวอร์ชัน:
Input และหน่วย:
สิ่งที่เปลี่ยน / สิ่งที่คงเดิม:
Expected result และเหตุผล:
Solver / stop time / initial conditions:
จุดวัด / ช่วงเวลาวัด / tolerance:
Actual result และไฟล์หลักฐาน:
PASS / FAIL / ยังสรุปไม่ได้:
สิ่งที่เรียนรู้และขั้นถัดไป:
```

- แยกช่วงเริ่มต้น (transient) ออกจากช่วงที่ใช้วัด steady-state
- การเทียบ waveform ต้องตรวจ time vector ก่อน หากเวลาต่างกันจาก variable-step solver ให้ตกลงวิธีจัดเวลาให้ตรงกัน ไม่เทียบ array ตามตำแหน่งโดยอัตโนมัติ
- ทดสอบข้อมูลผิดรูปแบบหรือค่านอกขอบเขตใน wrapper ให้ถูกปฏิเสธก่อนส่งไป simulation เมื่อถึงขั้นเขียน wrapper
- เริ่มจากตั้งค่าก่อน Run และรับผลเมื่อจบ ยังไม่ทำการควบคุมระหว่างรัน
- หากไม่ผ่าน ให้เก็บ error และแก้เฉพาะขั้นนั้น ไม่เพิ่มวงจรหรือส่วนเชื่อมต่อใหม่พร้อมกัน

## 7. จุดตัดสินใจและขอบเขตที่ไม่ขยายเอง

ต้องตกลงกับผู้ใช้ก่อน:

- เลือกโมเดลและยืนยันลำดับ Buck → rectifier → Python หรือปรับลำดับ
- เลือก parameter, expected result และเกณฑ์ผ่านก่อนแต่ละการทดลอง
- กลับไปแก้ Engine startup และกำหนดว่าใครรันอย่างไร หลังคำขอเดิมถูก Deny
- ดาวน์โหลดตัวอย่าง ติดตั้ง dependency หรือเพิ่มความซับซ้อนที่ไม่ได้ตกลงไว้

ยังไม่ทำใน phase นี้:

- เชื่อม Node/Express, Dashboard, Supabase, ESP32 หรือ deploy
- สร้าง charger เต็มระบบ สามเฟส/PFC, isolation design, battery CC–CV, thermal/loss optimization หรือ real-time control
- ต่อวงจรไฟฟ้ากำลังจริง
- reset Git, เปลี่ยน branch, ล้างไฟล์ หรือแก้งานเดิมใน `src`

หากกลับไปคุยเว็บเดิม ให้จำว่า **การกดยืนยัน CSV จะแทนข้อมูลฐานข้อมูลเก่า** ไม่มีเหตุให้ทำขั้นตอนนั้นระหว่างการทดลองนี้

## 8. วิธีสอนทีละขั้น

แต่ละรอบใช้ลำดับนี้:

**บอกเป้าหมาย → อธิบายคำสั่งหรือการคลิกหนึ่งขั้น → บอกผลที่ควรเห็น → ให้ผู้ใช้ลงมือและส่งผล → ตรวจ/อธิบาย → บันทึกผ่านหรือยังไม่ผ่าน → ค่อยไปต่อ**

- ผู้ใช้ต้องได้เรียนเหตุผล ไม่ใช่เพียงรับผลสำเร็จจาก agent
- ใช้หลักฐานที่ทำแล้ว ไม่ให้ผู้ใช้ทำ `cd`/`pwd` ซ้ำโดยไม่จำเป็น
- แยกคำสั่ง Terminal, Python และ MATLAB Command Window ให้ชัดทุกครั้ง
- ไม่ถือว่าการส่ง roadmap หรือการเปิดแชทเป็นการอนุญาตให้ทดลองทั้งหมด
- เมื่อผู้ใช้ต้องการปรับเป้าหมาย ให้ทบทวน scope และผลต่อขั้นถัดไปก่อนเปลี่ยนแผน

**ข้อความเริ่มต้นที่เสนอสำหรับแชททดลอง:** สรุปเป้าหมายสั้น ๆ แล้วให้ผู้ใช้ยืนยันว่าเริ่มเรียน Buck ก่อน ตามด้วย rectifier และ Python หรืออยากปรับลำดับ จากนั้นรอคำตอบก่อนเปิดโมเดลหรือ Run
