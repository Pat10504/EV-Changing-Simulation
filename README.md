# ระบบจำลองการจัดการพลังงานสำหรับสถานีชาร์จ EV

จำลองหลายสถานีชาร์จในพื้นที่ที่ใช้หม้อแปลงใหญ่ร่วมกัน อ่านโหลดรายช่วงเวลาจาก Supabase แล้วจัดสรรกำลังให้ตู้ที่มีรถชาร์จ โดยลดกำลัง **เป็นเปอร์เซ็นต์ตามสัดส่วนพิกัด** และรักษา **ขั้นต่ำ 12 kW ต่อตู้ active**

[แผนนำระบบขึ้นออนไลน์บน Railway, Supabase และ AWS](docs/deployment-plan.md)

## วิธีจัดสรรที่ใช้ตอนนี้

1. คำนวณโหลดพื้นฐานจากเปอร์เซ็นต์ของพิกัดหม้อแปลง หน่วย kVA
2. หางบ EV: `B = max(0, (ขีดจำกัด kVA − โหลดพื้นฐาน kVA) × PF)`
3. หาความต้องการ EV: `D = Σ(จำนวน active × พิกัดตู้ kW)`
4. แบ่งรอบแรกด้วยสัดส่วน `r₀ = min(1, B / D)` แต่ละตู้ได้ `พิกัด × r₀` (ไม่มี active ใช้ r₀ = 1)
5. ตรึงกลุ่มที่ต่ำกว่า 12 kW ไว้ที่ 12 kW แล้วแบ่งงบที่เหลือใหม่ตามสัดส่วนพิกัดของกลุ่มที่ยังลดได้ ทำซ้ำจนจัดสรรครบ
6. ถ้างบไม่พอแม้ทุกตู้อยู่ที่ขั้นต่ำ ให้แสดง **ยังเกินขีดจำกัด** และส่วนที่ลดไม่ได้ ระบบไม่เปลี่ยน active หรือพักตู้เอง

**เปอร์เซ็นต์ลดไป** = `100 − เปอร์เซ็นต์ที่เหลือ`; เมื่อมีตู้ชนขั้นต่ำ เปอร์เซ็นต์ลดสุดท้ายของแต่ละขนาดจะต่างกัน

ตัวอย่าง 50 MVA / limit 80% / PF 0.9 จากข้อมูลที่ตรวจวันที่ 14 พฤศจิกายน 2026:

| เวลา | งบ EV | ผลรอบแรก 50 / 150 kW | ผลสุดท้าย 50 / 150 kW | ผลหลังควบคุม |
|---|---:|---:|---:|---|
| 18:00 | 2,925 kW | 13.12 / 39.35 | 13.12 / 39.35 | 40,000 kVA |
| 18:55 | 2,304 kW | 9.48 / 28.44 | 12 / 24.45 | 40,000 kVA |
| 20:55 | 954 kW | 4.84 / 14.53 | 12 / 12 | 40,420 kVA — ยังเกิน 420 kVA |

กำลังในสองคอลัมน์กลางเป็น kW ต่อตู้ active ข้อมูล Supabase ชุดที่ตรวจมี 288 แถว โดย 35 แถวมีผลรอบแรกของตู้เล็กต่ำกว่า 12 kW: กระจายต่อสำเร็จ 25 แถว และอีก 10 แถวที่ 20:15–21:00 ยังเกิน limit การเปลี่ยนสูตรครั้งนี้ไม่ได้เปลี่ยนข้อมูลในฐานข้อมูล

## รันเว็บหลัก

ต้องมี Node.js ที่รองรับ dependencies ใน `package.json` และสร้าง tables ตาม `supabase/schema.sql` จากนั้นตั้งค่า `.env` ตาม `.env.example` โดยเก็บ service role key เฉพาะ backend

```bash
npm install
npm run p
```

เปิดหน้าเว็บตาม port ที่ Terminal แสดง (ค่าเริ่มต้น 3000):

- Dashboard: http://localhost:3000/dashboard
- อัปโหลด CSV: http://localhost:3000/upload
- สูตรและตัวอย่าง: http://localhost:3000/formulas
- ทดลอง MATLAB อัตโนมัติ: http://localhost:3000/dashboard?mode=matlab

ใช้ `npm start` เพื่อรันโดยไม่มี nodemon และ `npm test` เพื่อทดสอบสูตร การเลือกเวลา/พัก/เล่นต่อ และการแสดงผล

## เลือกเวลาจำลองและอ่านกราฟ

1. ตั้งค่าหม้อแปลง ขีดจำกัด และ PF แล้วเลือกเวลาในช่อง **เลือกเวลา** เช่น `18:35` (รายการมาจากข้อมูล Supabase จริง)
2. กด **ดูช่วงนี้** เพื่อคำนวณและแสดงผลเวลานั้นทันที พร้อมพักไว้ให้อ่าน ในโหมดตามเวลาจำลอง การ์ดและตารางจะแสดงแถวดังกล่าว
3. กด **เริ่ม / เล่นต่อ** เพื่อเดินไปแถวถัดไป เช่น `18:40` หรือเลือกเวลาใหม่แล้วกดเริ่มเพื่อเล่นจากเวลานั้นโดยตรง

ปุ่มลัด `12:30`, `18:35`, `20:55` เปิดดูและพักเช่นเดียวกัน โดยใช้ได้เฉพาะเมื่อมีเวลานั้นในข้อมูล ปุ่มพักหยุดที่ผลล่าสุด; รีเซ็ตล้างผลและกลับไปพร้อมเริ่มที่แถวแรก เมื่อเล่นถึงแถวสุดท้ายจะวนกลับแถวแรกตามเดิม

กราฟใช้ **Chart.js 4.6.1** ติดตั้งผ่าน npm และเสิร์ฟจากเว็บนี้ สีฟ้า = โหลดพื้นฐาน, สีเขียว = EV หลังควบคุม, สีม่วง = โหลดรวมก่อนควบคุม และเส้นประสีแดง = ขีดจำกัด ชี้กราฟเพื่อดูเวลา พร้อมค่า % และ kVA คลิกเพื่อเลือกเวลาของการ์ดและตาราง

กราฟภาพรวมแสดงทุกเวลาในข้อมูลรายวัน คลิกกราฟหรือเลือกเวลาเพื่ออ่านโหลด กำลังต่อตู้ และผลวัดของชุดที่เลือก กด **ตามเวลาจำลอง** เพื่อกลับไปดูแถวที่กำลังเล่น การดูย้อนหลังทำได้ขณะคิว MATLAB เดินต่อ

รีเฟรชหน้าเว็บแล้วจะคืนผลล่าสุดและกราฟจากเซิร์ฟเวอร์ได้ ตำแหน่งการเล่นอยู่ในหน่วยความจำของเซิร์ฟเวอร์ จึงไม่คงอยู่เมื่อรีสตาร์ต Node.js

API ที่เกี่ยวข้อง: `POST /api/simulation/start` รับ `start_time` แบบ `HH:MM` เพิ่มได้ (ไม่ส่ง = เล่นต่อ), `POST /api/simulation/seek` ต้องส่ง `start_time` และจะพักหลังแสดงผล, `GET /api/simulation/state` คืน `availableTimes` และ `lastResult` พร้อม `chartHistory` เวลาไม่ถูกต้องหรือไม่มีในข้อมูลจะถูกปฏิเสธโดยไม่เปลี่ยนผลเดิม

## ข้อมูลและหน้าจอ

อัปโหลดไฟล์สองชุด: ทะเบียน `charger_kW,total_units` และโหลด `time,base_load_percent,active_[ขนาด]kW` ราย 5 นาที จำนวน active ต้องไม่เกินจำนวนติดตั้ง ดูตัวอย่าง header และรายละเอียดใน [AGENTS.md](AGENTS.md)

ไฟล์ข้อมูลใช้งานจริงจัดเก็บนอก repo แล้วอัปโหลดผ่านเว็บ การยืนยันอัปโหลดจะ **แทนที่ข้อมูลเดิมใน Supabase** มี CSV template สำหรับดาวน์โหลดใน `src/public/templates/` ซึ่งไม่ใช่ข้อมูล fallback

Dashboard ฉบับออกแบบใหม่แสดง:

- โหลดรวมก่อน/หลังควบคุม โหลดพื้นฐาน และงบกำลังให้ EV พร้อมหน่วยชัดเจน
- กราฟพื้นที่ซ้อน Base + EV หลังควบคุม เทียบเส้นโหลดก่อนควบคุมและขีดจำกัด
- ผลรอบแรกก่อนใช้ขั้นต่ำ เทียบกำลังสุดท้าย และแยก `% ลดไป` / `% เหลือ`
- ข้อความเมื่อตู้ชนขั้นต่ำ รับการลดเพิ่ม หรือยังควบคุมให้อยู่ใน limit ไม่ได้

## ขอบเขตของผลจำลอง

- ขั้นต่ำ 12 kW เป็นกติกาทดลอง ไม่ใช่ข้อกำหนดสากลของรถทุกคัน
- ใช้ PF ร่วมและทิศทาง Q เดียวกันสำหรับ Base/EV ยังไม่คิดการสูญเสียตู้ (η = 1) จึงยังไม่ได้แยก AC input กับ DC output
- สมมติทุกตู้ active ต้องการกำลังเต็มพิกัดก่อนควบคุม ไม่มีข้อมูล SOC แรงดันแบตเตอรี่ หรือกำลังที่รถรับได้รายคัน
- ตู้พิกัดต่ำกว่า 12 kW จำกัดตามพิกัด พร้อมแจ้งว่าไม่รองรับขั้นต่ำนี้; ตู้ inactive ไม่ร่วมแบ่งกำลัง
- สถานะ `OVERLOAD` เทียบกับ limit ที่ตั้ง ไม่จำเป็นต้องเกินพิกัด 100% ของหม้อแปลง
- คำนวณด้วยความละเอียดเต็มก่อนปัดผลแสดง 2 ตำแหน่ง ตัวเลขต่อตู้ที่ปัดแล้วอาจคูณกลับไม่ตรงยอดรวมเล็กน้อย
- ยังไม่จำลองข้อจำกัดหม้อแปลงย่อย/สายป้อน ไม่มีการสั่งฮาร์ดแวร์; เชื่อม MATLAB เฉพาะการทดลองตู้ตัวแทนจากเวลาที่เลือก ไม่ใช่การจำลองเครือข่ายทั้งพื้นที่

## ทดลองวงจรจาก Dashboard

1. เปิด MATLAB และแชร์ `matlab.engine.shareEngine('EVChargingLab')` โดยโมเดลต้องอยู่ใน repo นี้และบันทึกการแก้ไขเรียบร้อย
2. เปิด Node ตามปกติ และเปิด Terminal อีกหน้าจาก root ของ repo:

```bash
experiments/python-matlab-engine/.venv/bin/python experiments/python-matlab-engine/web_app.py
```

3. Dashboard → เลือกเวลา เช่น 18:35 → **ดูช่วงนี้** → **ทดลองตู้ 50 kW ใน MATLAB**
4. หน้า `/circuit?id=...` ล็อกเวลาและกำลังจากผลคำนวณของเซิร์ฟเวอร์ไว้ ตรวจแรงดันอ้างอิง / SOC / เวลาวงจร แล้วกด **รัน MATLAB**
5. ดูกำลังเฉลี่ยช่วงท้ายเทียบเป้าหมาย พร้อมแรงดัน กระแส DC bus และกราฟผลจริง รันทีละงานและกลับมาดู URL เดิมได้ตราบใดที่เซิร์ฟเวอร์ยังไม่รีสตาร์ต

ตัวอย่างนี้ใช้ `I_ref = P_target × 1000 / V_reference` เป็นกระแสคงที่ ไม่ใช่ตัวควบคุมกำลังป้อนกลับ แรงดันอ้างอิง 400 V ไม่ได้ตั้งแรงดันจริงของแบตเตอรี่ พิกัด 50 kW / กระแสไม่เกิน 125 A เป็นขอบเขตการส่งคำสั่งทดลอง ยังไม่ได้เพิ่มตัวจำกัดกำลัง 50 kW ในวงจร ผลจริงอาจสูงหรือต่ำกว่าเป้าหมาย

ค่าเฉลี่ยถ่วงตามเวลาจากช่วงท้าย 20% ใช้ P(t)=V(t)I(t) จากข้อมูลเต็ม กราฟย่อเหลือไม่เกิน 1,200 จุด เกณฑ์ความนิ่งเบื้องต้นดูความต่างค่าเฉลี่ยสองครึ่งไม่เกิน 2% และช่วงแกว่งไม่เกิน 5%; ไม่ใช่การรับรองพิกัดวงจร เวลาจำลอง 0.2–2 s แยกจากเวลาโหลดราย 5 นาที และแต่ละรอบเริ่ม SOC ใหม่

หน้าเก่า `http://127.0.0.1:5050` ยังใช้ทดลองกระแส 20–100 A ได้ แต่แบ่งล็อกงานเดียวกับ API ใหม่ ไม่มีการสร้างผลวัดจำลองเมื่อ Python/MATLAB ไม่พร้อม ดูรายละเอียดใน `experiments/python-matlab-engine/README.md`

## ทดลองตาม load profile อัตโนมัติ

เปิด Node, Python และ MATLAB ที่แชร์ `EVChargingLab` ตามขั้นตอนข้างต้น จากนั้น:

1. เปิด Dashboard เลือก **จำลองพร้อม MATLAB** แล้วเลือกเวลาเริ่ม–สิ้นสุดในวันเดียวกัน เช่น 11:45–11:55 ได้ 3 แถว
2. ตรวจค่าหม้อแปลง ขีดจำกัด และ PF พร้อมแรงดันอ้างอิง (400 V) SOC เริ่มต้น (20%) และเวลาวงจร (0.5 s ต่อแถว)
3. กด **เริ่มจำลองพร้อม MATLAB** ครั้งเดียว เซิร์ฟเวอร์เก็บสำเนาข้อมูลโหลด จำนวนตู้ และค่าตั้ง จากนั้นทดลองทุกแถวที่มีตู้ 50 kW active แม้กำลังเป้าหมายเท่ากับแถวก่อน
4. การ์ดโหลดแสดงแถวที่กำลังทดลอง ผล MATLAB มาเติมในแถวเดิม แล้วคิวเดินต่อ Socket.IO แจ้งให้เว็บอ่านผลใหม่ เมื่อเปิด URL ของชุดนั้นอีกครั้งจะเห็นผลที่บันทึกไว้
5. เปรียบเทียบกำลังเป้ากับกำลังเฉลี่ยจากวงจร ดูค่าคลาดเคลื่อน V และ A ในตาราง กดจุดที่มีผลวัดหรือ **ดูกราฟ** เพื่อดูรายละเอียดรายแถว และดาวน์โหลด CSV ได้ในหน้าเดียว

ในช่อง **ดูรายละเอียดช่วงเวลา** กด **ประวัติ MATLAB ของเวลานี้** เพื่อเปิดผลที่เคยวัดจากชุดอื่นตรงเวลาเดียวกัน ชุดใหม่เก็บข้อมูลโหลดทั้งวันพร้อมค่าตั้ง สำหรับชุดเดิม กราฟใช้ข้อมูลที่เคยบันทึกในช่วงทดลองและเติมเวลาที่เหลือจากโหลดปัจจุบัน โดยระบุแหล่งข้อมูลใต้กราฟ

**ความหมายของแต่ละรอบ:** เป็นการทดลองอิสระของตู้ตัวแทนหนึ่งตู้ เริ่ม SOC และสถานะวงจรใหม่ทุกครั้ง ไม่ใช่การชาร์จสะสมของรถคันเดิม 5 นาทีใน load profile ไม่ได้ถูกแปลงเป็นพลังงานของการจำลองวงจร 0.5 s กำลัง DC จาก MATLAB ยังไม่ถูกนำกลับไปแทนโหลด AC ของหม้อแปลง

- **พักหลังจบรอบ** รอผลรอบปัจจุบันแล้วพักก่อนส่งรอบถัดไป กด **ทำต่อ** เพื่อเดินต่อ
- **หยุดชุดทดลอง** รอผลรอบปัจจุบันและยกเลิกแถวที่ยังไม่รัน เก็บผลที่ได้แล้วไว้ ไม่ฆ่า MATLAB ระหว่างแก้วงจร
- หาก Python/MATLAB ไม่พร้อมหรือรอบใดล้มเหลว ชุดจะพักและแจ้งสาเหตุ ไม่มีผลสมมติ กรณีรอบล้มเหลวที่ยืนยันแล้ว การกดทำต่อจะข้ามรอบนั้นและไปช่วงถัดไป โดยยังบันทึกสถานะล้มเหลวไว้
- หากขาดการเชื่อมต่อหลังส่งคำสั่ง ระบบตรวจรหัสงานเดิมก่อน ไม่ส่งงานนั้นซ้ำอัตโนมัติ ถ้า Python เริ่มใหม่จนไม่พบงานเดิม จะระบุว่ารอบล้มเหลว/ยืนยันผลไม่ได้
- เวลาไม่มีตู้ 50 kW active จะถูกข้ามโดยไม่รัน MATLAB หากงบไม่พอขั้นต่ำ 12 kW ยังแสดง `LIMITED` และ kVA ที่เกิน แม้วงจรจะรันสำเร็จ
- หน้า manual ของ Node ถูกกันไม่ให้แทรกชุดที่กำลังทำงาน ส่วนฟอร์ม Flask เดิมใช้ล็อก Engine ร่วมกัน ถ้ามีงานภายนอกแทรก คิวจะพักให้ตรวจสอบ

**การเก็บผล:** อยู่ใน `runtime-data/circuit-batches/` ภายในเครื่อง เป็นข้อมูล JSON ในไฟล์ `.snapshot` แยก metadata ของชุดและกราฟแต่ละรอบ เขียนไฟล์ชั่วคราวก่อนเปลี่ยนชื่อแทนไฟล์เดิม ไม่ติดตามใน Git ไม่เสิร์ฟเป็น static file และไม่อัปโหลด Supabase สำรองโฟลเดอร์นี้แยกต่างหากหากต้องการเก็บผลระยะยาว

เมื่อ Node เริ่มใหม่ ผลที่เสร็จยังอ่านได้ แต่ชุดที่กำลังรันจะพัก กดทำต่อเพื่อตรวจผลเดิมกับ Python แล้วจึงเดินคิว ไม่เริ่มรันเองหลังเปิดเซิร์ฟเวอร์ การตั้งค่าตัวเฝ้าไฟล์ใน `nodemon.json` แยกผลทดลองออกจาก source ที่ต้องรีสตาร์ต

ไฟล์หลัก: `src/services/circuit-batch.service.js` จัดลำดับงานและสถานะ, `circuit-batch-store.js` เก็บผล, `src/public/dashboard.html` และ `src/public/js/dashboard-matlab.js` แสดงโหลดและผลวงจร ใช้ Python API และ `run_dashboard_experiment.m` เดิม สูตรจัดสรรและตัวควบคุมวงจรไม่ได้เปลี่ยนเป็น feedback power control ในขั้นนี้

API: `POST/GET /api/circuit/batches`, `GET /api/circuit/batches/:id/dashboard` (ผลชุดและแถวโหลดปัจจุบัน), `GET /api/circuit/batches/:id`, `POST /api/circuit/batches/:id/action` (`start`, `pause`, `stop`), `GET /api/circuit/batches/:id/rows/:rowId`, `GET /api/circuit/batches/:id/export.csv`

## ห้องทดลองอุณหภูมิหม้อแปลง

เปิด **อุณหภูมิหม้อแปลง** จาก Dashboard หรือเข้า `/thermal` เลือกการทดลอง A (อากาศกับอายุฉนวน), B (ผล FAT ของแต่ละขั้นระบายความร้อน), C (ภาระเกินชั่วคราว) หรือ D (WTI และการลดภาระสาธิต) หน้าเว็บคำนวณจากเงื่อนไขของการทดลองในเบราว์เซอร์โดยตรง ใช้งานได้โดยเปิด Node server แม้ไม่ได้เชื่อม Supabase หรือ MATLAB

C เริ่มจาก 37.5 MVA หรือเลือกจุดอ้างอิง 50 MVA จาก B เพื่อเปรียบเทียบอุณหภูมิกรณีคงภาระกับกรณีเพิ่มเป็น 55–70 MVA โดยคำนวณทีละนาทีเป็นเวลา 10 ชั่วโมง ส่วน D เริ่มจาก 37.5 MVA และแสดงชั่วโมงเสื่อมเทียบเท่าสะสม โหมด D มีกรณีสาธิตลดเหลือ 50 MVA เมื่อจุดร้อนถึง 105 °C เพื่อเปรียบเทียบกับคงภาระเดิม เกณฑ์ WTI 110/120 °C ใช้แสดงสถานะสมมติในห้องทดลองนี้

## บัญชีสำหรับเข้าสู่ระบบ

ผู้ใช้ทุกคนใช้บัญชีร่วมหนึ่งบัญชีและใช้ทุกฟังก์ชันได้หลังเข้าสู่ระบบที่ `/login` ตั้ง `APP_USERNAME` และ `APP_PASSWORD` ในไฟล์ .env บนเครื่อง หรือใน Variables ของ Railway ก่อน deploy รุ่นที่มี Login เก็บรหัสผ่านเฉพาะฝั่งเซิร์ฟเวอร์ เซสชันสิ้นสุดเมื่อออกจากระบบ ครบ 8 ชั่วโมง หรือเซิร์ฟเวอร์รีสตาร์ต การสาธิตใช้เซิร์ฟเวอร์หนึ่ง instance

## การเชื่อมวงจรบนคลาวด์

Railway ใช้ตัวเชื่อมบน Windows EC2 ที่เชื่อมกลับผ่าน HTTPS และยืนยันด้วย `MATLAB_WORKER_TOKEN` รองรับทั้งรอบเดียวและคิวรายแถว Flask อยู่ที่พอร์ต 5050 ภายในเครื่องวงจร ดูการตั้งค่าและการทดสอบที่ [แผนนำระบบขึ้นออนไลน์](docs/deployment-plan.md)
